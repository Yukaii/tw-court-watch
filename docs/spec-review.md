# Spec Review & 實測勘誤（2026-11-19）

本報告根據 2026-11-19 實際抓取與測試 `csdi3.judicial.gov.tw`（`WHD1A03`、`WHD1A03B`、`ctstate`）及司法院開放資料現況，逐項檢核 [`original-spec.md`](original-spec.md) 的事實正確性、資料策略（尤其是「不做爬蟲」的決策）與產品設計矛盾。

---

## 1. 一句話總結

原規格抓對了核心痛點與法律紅線（不做評分排行、禁錄音拍照、不做個資），但有 **3 個會直接讓產品死掉或出包的重大問題**：

1. **「不做爬蟲、用靜態人工精選 JSON」會讓產品徹底失去用處** — 庭期每天過期，人工不可能維護；而實測顯示官方站其實直接提供乾淨的 **JSON API 與整批 UTF-8 CSV 下載端點**（不需要瀏覽器爬蟲、沒有 CAPTCHA），每天定時抓 1–2 次只需幾十個 HTTP 請求。
2. **實測發現大量「看似公開但其實不能旁聽」的庭期混在民事／刑事結果裡** — 光是台北地院今日一天 374 筆中，就有 54 筆是**調解／調解室**（不公開）、另有 `審理程序(不公開)`、`協商程序(不公開)`、`家非調`（家事藏在民事裡）及性隱私相關案件。而且原規格完全漏掉了最關鍵的欄位 **`dukd`（庭類）**。
3. **「公開觀庭筆記」卻用 `localStorage` 實作是自相矛盾** — 存 `localStorage` 只有自己看得到，根本不是公開筆記；應該明確切分「個人旁聽清單／私密筆記（純靜態）」與「公開觀庭筆記（需要後端與審核機制）」。

## 3. 官方端點實測結果（無需 Headless Browser）

實測確認 `csdi3.judicial.gov.tw` 無 CAPTCHA、無複雜反爬，只需要先 `GET` 取得 session cookie 與 `_csrf` token：

1. **分頁 JSON 查詢**：`POST /judbp/wkw/WHD1A03/QUERY.htm`
   - 參數：`_csrf`, `crtid`, `sys`, `startdt`（7 碼民國 `1151119`）, `enddt`, `pageNum`, `pageSize`（另可選 `crmyy`, `crmid`, `crmno`, `dunm`, `dpt`）
   - 回傳範例：
     ```json
     {
       "crtid": "TPD", "sys": "刑事", "dpt": "和",
       "crmyy": "115", "crmid": "易", "crmno": "000727",
       "dudt": "1151119", "dutm": "0929", "ducd": "6001",
       "dunm": "1樓國民法官第1法庭", "dukd": "宣判", "rsn": "傷害"
     }
     ```
2. **單次整批 CSV 下載（關鍵發現）**：`POST /judbp/wkw/WHD1A03/DOWNLOAD_RESULT_CVS.htm`
   - 同樣參數，**一個請求直接回傳該法院 × 類別 × 日期區間的全部筆數（UTF-8 with BOM CSV）**，完全不用翻頁！
3. **法庭清單 JSON**：`POST /judbp/wkw/WHD1A03/DUNM.htm`（`{crtid}`）
4. **國民法官字別 JSON**：`POST /judbp/wkw/WHD1A03B/CRMID.htm`（`{crtid, sys:'H'}`）
5. **全法院股別分配表 CSV**：`POST /judbp/wkw/WHD1A03/DOWNLOADALLCVS.htm`（格式：`法院,股別,法官,書記官,分機`）
6. **當日即時開庭進度**：`https://csdi3.judicial.gov.tw/judbp/ctstate/index.jsp`（BIG5 編碼表單 `POST getCtState_01.jsp`）

## 4. 「不做爬蟲」決策的深度審查與替代方案

### 為什麼原規格的「不做爬蟲 + 人工精選 JSON」行不通
- 產品核心主張是**「3 分鐘找到今天／這週可旁聽的庭」**。
- 光台北地方法院**單日**就有 374 筆庭期（刑事 225 + 民事 149），且每天都在變動、過期即消失。
- 人工維護 JSON 撐不過兩週就會變死站；若只做「連回官方站」，使用者仍得操作難用的官方 iframe，這專案就沒有存在價值。

### 關於開放資料與 `robots.txt` 的誠實評估
- **開放資料**：已確認 `opendata.judicial.gov.tw` 與 `data.gov.tw` **目前皆無庭期表 API／資料集**（僅有裁判書 API、統計、法拍等）。
- **`robots.txt`**：`https://csdi3.judicial.gov.tw/robots.txt` 目前為 `User-agent: *` / `Disallow: /`，頁面也有 `<meta name="robots" content="noindex, nofollow">`（主要目的為防止搜尋引擎長期收錄庭期與案號）。
- **資料性質**：庭期表**不含當事人姓名、地址等個資**，僅有法院、案號、法庭、股別、庭類、案由。

### 三種資料架構比較

| 方案 | 做法 | 請求量 | 優點 | 缺點／風險 |
|---|---|---|---|---|
| **A. 低頻定時同步（推薦）** | GitHub Actions / Cron 每天 1–2 次（如 06:30、18:30）呼叫 `DOWNLOAD_RESULT_CVS.htm`，每次間隔 1–2 秒，輸出靜態 JSON／SQLite（類似 `taipei-trash` 的 `scripts/data/update.ts` 流程） | 22 地院 × 2 類 = **44 req/次**；即使全台灣主要法院也僅 ~120–160 req/次 | 支援跨法院探索（「雙北今天有哪些言詞辯論／國民法官？」）、首頁秒開、不受官方維護斷線影響、對官方主機負擔極低 | 需留意 `robots.txt` 風險；建議對單筆庭期頁加 `noindex` 且自動清除過期庭期（不留長期歷史索引） |
| **B. On-demand 快取代理** | Serverless Function / Cloudflare Worker 依使用者查詢條件代打 `QUERY.htm`，依 `(crtid, sys, date)` 快取 30–60 分鐘 | 僅在使用者查時才發請求 | 不需維護 cron、可查任意日期與法院、沒有批次抓取問題 | 無法做「今日全雙北推薦／國民法官總覽」這類探索頁；官方慢或維修時前端會卡 |
| **C. 混合制（A + B）** | 每天定時同步「未來 14 天」熱門／全部主要法院做首頁探索與篩選；若使用者查冷門日期或點「重新檢查」再 fallback 單次查詢或外連 `WHD1A03.htm?crtid=...` | 同 A + 極少量即時請求 | 兼顧探索體驗與彈性 | 開發複雜度稍高，可先做 A 再視需求加 B |

**建議**：MVP 採 **方案 A**（先抓六都／雙北地院＋高等法院＋行政法院＋所有 22 地院的國民法官，或直接全 22 地院 + 高院 + 行政法院，每日 2 次，1.5 秒節流），並落實 4 項禮貌與合規措施：
1. 固定低頻同步（絕不高頻輪詢），明確 User-Agent，錯誤時退避重試。
2. 過期庭期自動下架（僅保留今日～未來 14 天），對庭期詳情頁加上 `noindex, nofollow`，尊重官方不讓搜尋引擎長期留存庭期的立場。
3. 絕不存當事人個資，每筆標註資料更新時間（`synced_at`）並附「到司法院查詢頁確認（`?crtid=...`）」連結。
4. 同時可向 `data.gov.tw` 提交「庭期表開放資料」需求建議，未來官方開放即可無痛切換。

## 5. 旁聽實務與資料清理的關鍵缺漏（實測發現）

### 5.1 必加欄位 `dukd`（庭類）— 決定「能不能旁聽、值不值得去」
實測台北地院單日（2026-11-19）374 筆資料的 `dukd` 分布：
- **極適合旁聽**：`審理`（50）、`言詞辯論`（74）、`辯論`（2）、`調查`（12）— 有實質攻防、證人詰問或辯論。
- **短時間／程序性**（加標籤提醒新手）：`準備程序`（100，通常 5–15 分鐘整理爭點）、`宣判`（77，通常不到 1 分鐘唸主文）、`訊問`（3）、`勘驗`（1）。
- **不可旁聽（必須預設濾除！）**：
  - `調解`、`試行調解`、`調解程序`（單日 54 筆，佔 **14.4%**！）
  - `審理程序(不公開)`、`協商程序(不公開)`（任何 `dukd` 含 `不公開` 或 `協商`）
  - 法庭名稱 `dunm` 含 `調解室`、`協商室`、`個別詢問室`、`評議室`

### 5.2 不公開／敏感案件過濾規則（需要更精準）
- **必擋（不列入可旁聽清單）**：
  - `sys === 'I'`（少年）或法院 `crtid === 'KSY'`（高雄少年及家事法院）
  - `crmid` 以 `家`、`婚`、`監`、`少`、`護` 開頭（家事與少年事件）
  - `dukd` 含 `不公開`、`調解`、`協商`；或 `dunm` 含 `調解室`、`協商室`、`詢問室`、`評議室`
  - `rsn` 含明確依法不公開之性侵害／兒少性剝削／性隱私案由（如 `妨害性自主`、`妨害性隱私`、`兒童及少年性剝削`）
- **需注意的邊界案例**：
  - 實測國民法官案件中出現 `家庭暴力罪之殺人等`、`家庭暴力罪之遺棄致死` — 這些屬於**刑事殺人／傷害致死案**（未必不公開，除非 `dukd` 標示不公開或法官當庭裁定），不宜只因出現「家庭暴力」四字就誤殺，而是依 `dukd`＋案件性質審慎處理，並一律標註「是否實際公開仍以開庭現場法官裁定為準」。

### 5.3 院區與地址陷阱（不能一法院只寫一個地址）
- 實測 `TPD`（臺灣臺北地方法院）的結果裡直接包含 `台北簡易庭第7法庭`！
- 台北地院本院在**博愛路 131 號**，但**台北簡易庭**在重慶南路一段 126 巷 1 號，**新店簡易庭**在新店區中興路一段 248 號，**寶慶院區**又在另一個點。
- 法院 metadata 必須支援「院區 / 法庭前綴 → 實際地址與捷運站」的對應，否則會把旁聽民眾導航到錯的建築物。

### 5.4 穩定 ID 設計
官方資料沒有原生 primary key，應使用確定性 composite ID（例如 `${crtid}-${sysCode}-${crmyy}-${crmid}-${crmno}-${dudt}-${dutm}`），才能讓「我的清單」、`.ics` 匯出與未來的觀庭筆記在每日重新同步後依然對應得到同一場庭。

## 6. 產品範圍與技術選型審查

### 6.1 觀庭筆記的架構矛盾（MVP 範圍重整建議）
原規格 §3 說 MVP 要做「公開觀庭筆記，不需登入也能看」，§9 卻說「先用 localStorage＋匯出 JSON」。這兩者互相矛盾。建議二選一：
- **路線 1（推薦先上線）**：**MVP 聚焦「極致好用的台灣旁聽找庭工具」**
  - 真實每日同步庭期（含雙北／全台法院、庭類篩選、國民法官標記、自動濾除調解與不公開）
  - 庭類白話解說（「新手推：審理／言詞辯論」、「30 秒快閃：宣判」）
  - 院區正確地址／交通／當日開庭進度連結（`ctstate`）
  - 旁聽新手指南 + 我的清單（`localStorage`）+ `.ics` 行事曆 + 個人私密觀庭筆記（`localStorage` + Markdown 匯出）
  - **V2 再上「公開觀庭筆記」**：配真正的輕量後端（Cloudflare D1 / Supabase / Turso）＋匿名防濫用（Turnstile）＋個資關鍵字預檢／檢舉下架機制。
- **路線 2**：若 MVP 就要「大家看得到彼此的觀庭筆記」，就從一開始接輕量 DB（如 Cloudflare D1 或 Supabase），不要浪費時間假裝 `localStorage` 是公開平台。

### 6.2 技術棧對齊
原規格直接預設 Next.js + Vercel，但觀察 `~/Projects/Personal/taipei-trash`（`garbage.yukai.dev`）的慣用架構是 **Bun + Vite + React 19 + Tailwind CSS v4 + Biome + TypeScript + 定時更新資料腳本**。
- 如果選**路線 1（純靜態前端 + 定時同步 JSON）**：沿用 **Vite + React + Tailwind + Bun**（跟 `taipei-trash` 完全同套肌肉記憶）最輕量、部署 Vercel 或 Cloudflare Pages 都免費秒開！
- 如果選**路線 2（含公開筆記 DB / SSR / On-demand API）**：Next.js（Vercel）或 Astro / React Router + Cloudflare Workers/D1 都更合適。

## 7. 開始寫程式前待拍板的 5 個關鍵決定

1. **資料同步範圍**：先同步「全台主要法院（22 地院 + 高院 + 行政/智財法院）」還是先「北北基桃」？（全量也只要 ~80–120 req/天，寫一次通用 parser 其實差不多）
2. **資料抓取方式**：採 **方案 A（GitHub Actions 每日 2 次同步靜態資料）**，還是 **方案 B/C（Serverless on-demand 快取代理）**？
3. **MVP 觀庭筆記定位**：先做「純前端個人筆記 + Markdown 匯出（路線 1）」，還是 MVP 就接 DB 做「公開觀庭筆記（路線 2）」？
4. **技術棧**：沿用 `taipei-trash` 同款 **Bun + Vite + React + Tailwind + Biome**，還是改用 **Next.js**？
5. **產品名稱與網域**：中文名（旁聽／觀庭方向）與英文 repo 名稱（目前資料夾暫定 `tw-court-watch`）。
